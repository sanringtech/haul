# Business Constitution: AI 用量監控小工具

> 這份文件不是 PRD（不寫 user story / tech stack / API / 頁面 / 部署）。
> 這份文件不是 Charter（不寫範圍邊界 / 分批計畫 / 停止條件）。
> 它只回答一件事：這個業務領域的規矩是什麼——即使換掉所有技術棧、改寫所有程式，這些規則仍然成立。

---

## 1. 業務目的 (Business Purpose)

- **這個領域服務的對象**：其他開發者（不只是業務 owner 自己用）
- **這個領域要解決的核心問題**：讓開發者在桌面隨時看到 Claude / Codex / DeepSeek / Kimi / Grok 這幾家 AI 服務的剩餘用量，不用切換去看各家網站或 CLI 輸出（AI 改寫，綜合 §0 開場答案與後續訪談推論）。**2026-08-31 修訂**：同一位開發者名下常常同時掛多個帳號（例如兩個 DeepSeek 帳號、兩個 Claude 訂閱、或同時有 Claude 訂閱又有 Claude API key），核心問題因此擴充為：不只是「看四五家的用量」，是「看清楚自己名下每一個帳號各自的用量」（見 §3 R1/R5）。**2026-09-03 修訂**：核心問題再擴充一層——除了看「現在還能不能用」，也要在本機留下可事後對帳的用量／額度紀錄（流水帳），供使用者自行稽核；即時配額狀態與歷史紀錄是兩種資料，互不頂替（見 §6）
- **明確不在這個領域內的問題**：
  - 不做用量趨勢預測（記錄已經發生的用量／額度 ≠ 預測未來）
  - 不做自動介入（例如自動切換帳號、自動阻擋任務執行）
  - 不執行帳號登入流程、不索取密碼
  - Phase 1 不做多人使用者用量拆分/歸屬標記——業務 owner 已明確拍板此功能是 **Phase 2 候選項目**，非本期範圍（見 §10）
  - 不做雲端託管或代管他人帳本（呼應 I1：任何紀錄都不可離開使用者本機）

## 2. 領域角色 (Domain Roles)

| 角色 | 業務職責（這個角色「做什麼業務動作」）|
|---|---|
| 使用者 | 透過自己已登入 / 已提供憑證的各 AI 服務帳號，查看該帳號的即時用量狀態，並檢視／匯出本機流水帳以自行稽核 |

> 業務 owner 明確拍板：Phase 1 只有這一個角色，不區分「帳號擁有者」與「共用帳號的使用者」。多人共用帳號時的用量歸屬，留待 Phase 2。

## 3. 核心業務規則 (Core Business Rules)

- **R1**（**2026-08-31 修訂**）：支援的範圍是「AI 類型」與「存取類型」兩個獨立維度的組合，不是寫死的固定清單：
  - **AI 類型**：Phase 1 支援 Claude / Codex / DeepSeek / Kimi / Grok，可擴充
  - **存取類型**：訂閱制（讀本機 CLI 使用紀錄或官方 session）／ API key 制（使用者提供 key 呼叫官方 balance/usage 端點），**兩者不是綁死在特定 AI 類型上**——同一個 AI 類型可能兩種存取類型都有（例如 Claude 訂閱 + Claude API key 是兩個完全獨立的帳號）
  - **帳號**：使用者可以在同一組（AI 類型 × 存取類型）底下新增多個帳號（例如兩個 DeepSeek API key 帳號），每個帳號獨立追蹤
- **R2**（**2026-08-31 修訂，泛化成存取類型而非寫死特定 AI**）：本工具不執行任何登入流程、不碰密碼。**訂閱制帳號**：只讀取官方 CLI／官方 session 已存在本機的資料來查詢用量，不需要使用者額外輸入憑證。**API key 制帳號**：由使用者自行提供 API key，工具用它呼叫官方用量端點。所有憑證 / key 只留在使用者本機，沒有伺服器接收或保存任何使用者資訊
- **R3**：本地估算出來的用量數字，UI 上必須明確標示為「估算值」，不可呈現為官方精確數字
- **R4**：本工具僅供查看用量與本機流水帳，不做用量趨勢預測、不做自動介入（例如自動切換帳號、自動阻擋操作）、不執行帳號登入流程。留下已經發生的紀錄並匯出，不屬於預測、也不屬於自動介入
- **R5**（**2026-08-31 新增**）：同一 AI 類型底下的多個帳號，彼此是**獨立的實體**——各自的連線狀態、用量數字、取消追蹤/關閉顯示操作都互不影響，不合併計算或合併顯示。帳號的識別標籤：能自動偵測身份的（例如訂閱制的帳號 email）自動帶入當標籤；偵測不到的（API key 制）**必須由使用者輸入暱稱才能新增帳號**。所有標籤（不論自動或手動）事後都可以讓使用者重新命名

## 4. 業務狀態機 (State Machines)

> **2026-08-31 修訂**：以下兩個狀態機的適用單位是「帳號」，不是「AI 類型」——一個 AI 類型底下有 3 個帳號，就有 3 組獨立的用量狀態與連線狀態（呼應 R5）。

### 用量狀態

```
正常 (0-80%, 綠) ──超過閾值──> 接近上限 (閾值-99%, 橘) ──到 100%──> 超額/額度用盡 (紅)
```

**合法轉換**：
- 正常 → 接近上限：用量超過閾值（預設 80%，使用者可調整，範圍 50%–95%）
- 接近上限 → 超額/額度用盡：用量達到 100%

**禁止轉換**：
- ❌ 任何用量狀態 → 自動阻擋 / 切斷任務：本工具僅顯示，不做自動介入（呼應 R4）

### 來源連線狀態

```
尚未設定 (灰) ──使用者提供憑證/key──> 有效 (綠)
                                    有效 (綠) ──被撤銷/格式錯誤──> 失效 (橘)
                                    有效 (綠) ──到期──> 過期 (紅)
```

**合法轉換**：
- 尚未設定 → 有效：使用者提供憑證或 API key
- 有效 → 失效：key 被撤銷或格式錯誤
- 有效 → 過期：token 到期（時間性問題）

## 5. 不可變約束 (Invariants)

- **I1**：本工具沒有伺服器，任何使用者的憑證 / API key / 用量資料，任何時刻都不可離開使用者本機，不可上傳到任何外部伺服器
- **I2**：本工具在任何情況下都不執行登入流程、不索取或儲存帳號密碼；若使用者主動提供 API key（DeepSeek / Kimi 情境），會將其儲存在使用者本機，但沒有伺服器接收或保存
- **I3**：任何來自本機估算（非官方即時 API）的用量數字，UI 上任何時候顯示都必須帶有「估算」標示，不可單獨呈現成官方精確數字

## 6. 業務術語表 (Glossary)

| 術語 | 定義 | 不是 |
|---|---|---|
| 估算值 | 由本工具依本機使用紀錄檔案自行加總推算出的用量數字 | 官方即時精確數字 |
| 官方即時數據 | 直接來自服務商官方用量 / 帳單查詢 API 的數字 | 本地估算值 |
| 連線狀態 | 某個來源的憑證 / API key 目前是否可用（有效 / 失效 / 過期 / 尚未設定四態） | 用量本身的多寡 |
| 時間窗口用量 | 訂閱制來源（Claude / Codex）在特定週期（如 5 小時滾動窗、每週）內已使用的量，週期到了會重置 | 永久累計總量 |
| 剩餘額度 | API key 制帳號帳戶餘額對應的可用量，用多少扣多少，不會自動重置 | 時間窗口用量 |
| AI 類型 | 提供服務的 AI 供應商（Claude / Codex / DeepSeek / Kimi / Grok，可擴充） | 存取類型（同一 AI 類型可能有多種存取類型） |
| 存取類型 | 查詢用量的方式：訂閱制（讀本機 CLI/官方 session）或 API key 制（使用者提供 key 呼叫官方端點） | AI 類型（不是綁定特定 AI，任一 AI 類型理論上都可能兩種都有） |
| 帳號 | 一個「AI 類型 × 存取類型」組合底下，使用者實際新增的一筆追蹤實體，有自己的標籤、連線狀態、用量 | AI 類型本身（AI 類型是分類，帳號才是實際被追蹤的東西） |
| 即時配額狀態 | 官方用量／餘額端點回報的「現在還能不能用」（時間窗口百分比、重置時間、或 API key 剩餘額度） | 流水帳裡的歷史加總或估算金額 |
| 流水帳 | 本機保存的用量／額度紀錄，供事後對帳與匯出（可含官方配額快照、餘額快照、以及依本機使用紀錄加總的 token／估算金額） | 即時配額狀態；也不是對未來用量的預測 |

## 7. 業務決策 (Business Decisions)

### Decision 1: 為什麼估算值必須標示，不能當精確數字顯示

- **決策**：本地估算的用量，UI 一律標示為估算
- **理由**：訂閱制來源沒有公開即時配額 API，本地估算跟官方實際扣除機制可能有落差
- **替代方案（拒絕）**：把估算值當精確數字顯示 —— 拒絕原因：會讓使用者誤判剩餘額度而踩雷

### Decision 2: 為什麼不做自動介入（自動切帳號 / 阻擋任務）

- **決策**：僅顯示用量狀態，不做任何自動介入
- **理由**：這是「監控」工具的定位，不是「管理/控制」工具；而且工具本身是唯讀通訊層，本來就沒有攔截其他 CLI 行為的機制
- **替代方案（拒絕）**：接近上限時自動阻擋 —— 拒絕原因：超出工具定位，也沒有技術上的攔截點

### Decision 3（2026-08-31 新增）：為什麼「AI 類型」跟「存取類型」要拆成兩個獨立維度

- **決策**：R1 不寫死「這家 AI = 這種存取類型」，改成兩個維度自由組合
- **理由**：業務 owner 發現實際情況是 Claude / Codex / Kimi 同時有訂閱制跟 API key 制（兩種計費互相獨立），只有 DeepSeek 目前只有 API key 制；寫死會導致「Claude API key」這種真實存在的帳號無法被建模
- **替代方案（拒絕）**：繼續把存取類型寫死在特定 AI 類型上（原始 R1/R2 的寫法）—— 拒絕原因：不符合實際情況，且每次新增一種組合都要改業務規則，不可擴充

## 8. 取消 / 沖銷 / 退回的規矩 (Reversal Semantics)

- **取消追蹤（完全移除）**：把該**帳號**（2026-08-31 修訂：單位是帳號，不是 AI 類型，同類型的其他帳號不受影響）從追蹤清單移除，並**全部刪除**該帳號本機儲存的 API key 與流水帳／估算歷史資料（呼應 I1「不留使用者資訊」的精神）
- **關閉顯示**：保留設定與資料，只是不顯示；之後可重新開啟繼續顯示

## 9. 時間 / 期間 / 截止規矩 (Temporal Rules)

- **自動刷新頻率**：預設 1 小時，使用者可調整為 5 分鐘 / 2 小時 / 純手動更新
- **歷史資料保留期**：預設 3 天，使用者可調整為 5 天 / 一週 / 手動清除

## 修訂紀錄：2026-08-31 多帳號支援

> 起因：業務 owner 在使用過程中發現真實需求——「我目前有兩個deepseek帳戶」「我有兩個claude訂閱帳號」「我同時有claude訂閱帳號跟claude api key」。走了一次憲法修訂訪談（非從零重新訪談，針對受影響章節）。

### ✅ 使用者親口答案（verbatim）

- 起因：「其實有多重的需求呢？比如說我目前有兩個deepseek帳戶？...我有兩個claude訂閱帳號可以怎麼處理？或者我同時有claude訂閱帳號跟claude api key」
